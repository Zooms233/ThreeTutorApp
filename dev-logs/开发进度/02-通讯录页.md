## 设计的两个关键决定

### 1. 世界资源平铺，拆掉 TUTOR 中间层

原结构是世界目录下再挂 `TUTOR/tutor_a.json`，后来决定平铺：

```
世界/<世界名>/         世界/<世界名>/
├── LEARNER.json       ├── LEARNER.json
└── TUTOR/             ├── tutor_a.json
    ├── tutor_a.json   ├── tutor_b.json
    ├── tutor_b.json   └── tutor_c.json
    └── tutor_c.json
```

理由：世界只承载 4 个角色档案，没有其他资源需要分类；平铺后导入代码少了预建目录一步，pubspec 的 assets 声明也减半。Flutter 的 assets **不递归包含子目录**，之前每层都要单独声明。

### 2. 角色数据懒加载：点击展开时才读取

列表页只需要世界名（目录名），扫一遍目录即可；角色档案在**首次展开该世界时**才读取，缓存起来，收起再展开不重复读。理由：

- 列表显示前不需要任何文件内容，提前读纯属浪费
- 点击只读一个世界，出错面小
- 详情页同理：进入档案页才读完整 JSON

## 学到的东西

### Flutter 生命周期与状态

- **initState**：页面"出生"时执行一次的地方（State 挂在 widget 树上时）。适合启动即加载数据：这里调一次 `_loadWorlds()`，之后 setState 只刷新界面、不再重读磁盘。build 会被反复调用（setState、切 tab、窗口变化都会触发），所以绝不能把读文件放进 build。`super.initState()` 是规矩，先执行 Flutter 自身的初始化。
- **mounted 检查**：await 会让代码暂时挂起，把控制权交出去——在等待磁盘响应的这段时间里，用户可能已经切走页面、State 被销毁。这时再 setState 会崩溃：`setState() called after dispose()`。所以每条 await 之后先写 `if (!mounted) return;`——"页面还活着吗？活着才继续操作界面"。用 context 之前同理（context 挂在页面上，页面销毁后也失效）。这是异步 UI 编程的标准安全带。
- **setState 刷新模式**：数据改变 → setState → build 重建。页面标准流程：读数据 → 存字段 → setState → build 显示。
- **await 之后的顺序**：await → mounted 检查 → 用结果。

### 布局与组件

- **mainAxisSize: MainAxisSize.min**：Column 的主轴是垂直方向，默认 `max` 会撑满整个可用高度——内容会被挤到顶部，外层 Center 无处可居。`min` 让 Column 只包住内容，Center 才能真正把它居中。
- **ScaffoldMessenger.of(context).showSnackBar()**：底部弹出提示条，设置 duration 后自动消失，适合"导入结果"这类一次性轻量反馈（重反馈用 AlertDialog 弹窗）。`of(context)` = 查找当前页面所属的提示条管理处。颜色不用手动设置：主题色板自动配出"深底白字"，换肤时自动跟随。
- **PopupMenuButton**：右上角弹出菜单，适合"常驻但不常用"的入口。删除这类危险操作走**两级对话框**：第一级列出世界供点选，第二级红字按钮二次确认（`TextButton.styleFrom(foregroundColor: Colors.red)`），防止误删。
- **三态界面模式**：加载中（转圈）/ 空状态（提示+引导按钮）/ 有数据（列表），分别用 `_loading` 和列表空不空判断，这是列表页的通用骨架。

### 存储层与数据

- **返回 Directory 而不是 String 路径**：Directory 只是"封装了路径的对象"，构造零开销、不动文件系统。消费方几乎都要做 IO（existsSync/create/delete），直接拿 Directory 省去每次转换；只要路径时 `.path` 取出来即可。
- **跨平台路径分隔符**：Windows 是 `\`，Linux/macOS 是 `/`，写死任何一个都会在另一个平台出错。`Platform.pathSeparator` 自动取当前系统分隔符。取路径最后一段（世界名）的惯用写法：`entity.path.split(Platform.pathSeparator).last`。
- **同一个 API 在不同平台表现可能不同**：`uri.pathSegments.last` 在 Windows 上会因尾斜杠取到空字符串，静态分析发现不了，真实运行验证才能暴露。
- **懒加载 + 缓存**：列表只扫目录名；角色档案在首次展开时才读，`Map<世界名, 数据>` 缓存，收起再展开不重复读；删除数据时同步清理缓存和展开状态。
- **导入的幂等性**：逐个检测重名、已存在跳过不覆盖——重复导入不破坏用户数据，这是导入功能的底线。

### 工程细节

- **字体不打包，引用系统字体**：打包字体要承担体积（思源黑体 25MB）和版权（微软雅黑等系统字体内嵌分发受限）双重成本。`fontFamily: 'Microsoft YaHei'` 引用系统已装字体名，零体积；其他平台没有该字体就自动回退系统默认（Android 思源黑体），观感依旧正常。
- **注释写"业务意图"不写 API 解释**：`//从完整路径中取出最后一段，即世界名：...\世界\教令院 → 教令院` 比 `//uri 统一用 / 分隔` 好懂——用例子说话，注释的目标读者是不懂 API 的将来的自己。

## 经验与反思

"一个方法一个方法写、逐个审查"的节奏在数据层效果很好：写一个、解释一个、审一个，每步都小到可以完全理解。相比第 1 节失败的 storage.dart 大冒进，这次同样的文件分 5 次对话完成，零返工。

带注释的代码本身就是学习笔记——每个方法、每个晦涩的写法都留注释，审查时用"这句是什么意思"的方式把知识点过一遍。

真实运行验证的价值超出预期：世界名空白这种问题，靠静态分析根本发现不了（分析全部通过），必须跑起来看。诊断手法也学到一招：用 SnackBar 临时显示数据，点一下就知道读到了什么。
